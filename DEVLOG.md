1.  issue 1: data collection memory leak
    SYMPTOM: i encountered a memory leak in my data collection code. i initially suspected this after checking the amount of trip/vehicle/alert files that had been collected over the weekend. i found that only ~1990 files had been collected. since these are downloaded every 30 seconds, i calculated an upper bound of number of files to be ~5430. however since the buses don't run overnight, i was expecting about ~4300 files per file type. i knew that something must be wrong.
    DETECTION: when i checked the status of the app, i saw a recent crash and a current memory of 131 mb which was very suspicious. i then checked the journal for restarts, which showed numerous restarts, some which were scheduled restart jobs, and numerous that were triggered by the linux oom killer. these crashes seemed to occur exactly 7.5 hours apart, which indicated to me that the memory was ballooning at a steady rate until it hit the vm max of 1 gb which then causes it to restart.
    ROOT CAUSE: after reviewing my data collection code, i realized that every thirty seconds i was saving the decoded feed from the metro requests to a single protobuf message object (on RAM). however this object had been created ONCE OUTSIDE of my main loop. as a result, since i was reusing one object for each parse, each new set of parse data (every thirty seconds) was being stored on top of the previous data in this object and the memory was never being freed since the object was never discarded. therefore the object's memory would balloon until the RAM usage hit 1gb, at which point linux oom would kill the process.
    SOLUTION: to solve this memory leak, i simply moved the object creation to within my main loop so that now, the decoded feed object is created fresh every thirty seconds, removing the reference to old object, therefore it is garbage collected when the new object is created.
    VERIFICATION: i ran my updated code for an hour. this run began with memory usage at 37.4 mb. based on previous data, i expected that my old code would've caused a peak memory usage of around 150 mb (growth rate of about 110 mb / hour). however, it remained flat at about 30-40 mb for the first hour post-fix, hitting a peak of 41.4 mb. yay!
